# 7. Manage schema with Flyway migrations instead of Hibernate `ddl-auto`

## Status
Accepted

## Context
Schema was managed by Hibernate's `ddl-auto: update`, which mutates the database automatically to match the entities at startup. That gives no versioned history of schema changes, no reviewable diff of what changed between deployments, and no reliable way to apply the same schema to a fresh database (CI, a new environment) versus an existing one without relying on Hibernate to infer it correctly every time.

## Decision
Add Flyway (`flyway-core`, `flyway-database-postgresql`) and manage schema through versioned SQL migrations under `src/main/resources/db/migration`.

- The existing schema (originally generated by `ddl-auto: update`) was captured as `V1__baseline.sql`.
- `spring.flyway.baseline-on-migrate: true` with `baseline-version: 1` lets Flyway treat V1 as already applied on databases that already have this schema (e.g. the local dev Postgres volume), while still running V1 normally on any empty database.
- `spring.jpa.hibernate.ddl-auto` changed from `update` to `validate` — Hibernate now only verifies entities match the schema at startup; Flyway migrations are the only way to change it going forward.
- The test profile (H2, in-memory) keeps `ddl-auto: create-drop` and explicitly disables Flyway (`spring.flyway.enabled: false`).

## Other Considerations

**Running Flyway against H2 in tests too**
- Would give test coverage over the migration SQL itself, not just the entity mappings.
- Rejected for now — favors keeping the test suite fast and Docker-free. Trade-off accepted: bugs in migration SQL won't be caught by `./mvnw test`, only by running against real Postgres (local Docker Compose, or CI/staging).

**Dropping the local Postgres volume and starting from an empty database**
- Would simplify the baseline (no need for `baseline-on-migrate`).
- Rejected — the existing `postgres_data` Docker volume has local dev data worth keeping.

## Consequences

- Schema changes now go through new versioned migration files (`V2__...`, `V3__...`, etc.) reviewed like any other code change, instead of being inferred implicitly by Hibernate at startup.
- `ddl-auto: validate` catches table/column/type/nullability drift between entities and the database at startup, but does **not** validate CHECK constraints, unique constraints, or FK `ON DELETE` behavior — those still require a migration to be written deliberately and are not enforced by Hibernate if forgotten.
- Since Flyway is disabled for the H2 test profile, the test suite verifies entity/repository behavior but does not exercise the migration SQL directly.
